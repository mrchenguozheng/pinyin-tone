# 维护

两条线同时在维护。这一页说明哪条线收哪种改动，这样收到一份报障时不必先由作者决定才动手。

| 线 | 分支 | dist-tag | 收什么 |
| --- | --- | --- | --- |
| 3.0 | `master` | `latest` | 新功能、API 改动、修复 |
| 2.x | `maintain/2.x` | `legacy`，固定指 2.5.2 | 只收回归修复 |

- **修复先进 `master`。** 只有当 bug 出在 2.x 自己的行为上（2.x 自己写错过，而不是 3.0 引入的），
  才回迁到 `maintain/2.x`，且只能发补丁：`2.5.3`，不发 `2.6`。
- **`maintain/2.x` 不收新功能、不改 API。** 那条线冻结在 2.5.2 的接口上：同样的三个导出、同样的
  签名。`pinyin-tone/v1` 在那条线上同样是删除状态。
- **`2.4.1` 保持弃用。** `legacy` 不会从 `2.5.2` 上挪开；2.4.1 仍可安装，供当初锁了它的人使用，
  但它不是维护目标，它的 `/v2` 切片行为也不会回来。
- **发版要两个 job 都绿。** `npm test`（含 `build-cjs.mjs --check`、mocha、`tsc --noEmit`）加
  `npm run pack:check`。`maintain/2.x` 有自己的 CI，所以回迁的改动必须在那边也绿 —— 只在
  `master` 上绿，不能说明 2.x 还好着。
- **两条线的修法不同时，就是两个提交。** 2.x 上有 3.0 删掉的代码，同一个 bug 在两条线上可能需要
  不同的改法。CHANGELOG 的条目写明这一版发在哪条线；迁移文档只描述行为，不叙述历史。
